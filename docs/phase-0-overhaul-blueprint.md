# Phase 0 Overhaul Blueprint

Branch: `codex/phase-0-overhaul-blueprint`  
Base branch: `codex/system-overhaul`  
Goal: Define the production-grade overhaul plan before splitting implementation into phase and task branches.

## Product Direction

The project should evolve from a single-upload AI trimming tool into a production-quality academic prototype for AI-assisted lecture and MOOC video editing.

The target product is an education-first desktop video editor that can accept raw teaching material, analyze it with local/API/hybrid AI providers, propose an editable plan, let the teacher review it, and export polished videos for YouTube, LMS platforms, social clips, or audio-only use.

This blueprint uses external tools such as KIRA, Descript, OpusClip, HyperFrames, Remotion, Premiere Pro, and DaVinci Resolve only as feature inspiration. No proprietary UI, code, branding, or private implementation details should be copied.

## Current System Audit

### Current Strengths

- Backend is already structured around FastAPI, SQLAlchemy, and a multi-agent processing pipeline.
- Current five-agent model maps well to the original FYP methodology:
  - Agent 1: transcription and alignment.
  - Agent 2: content/RAG understanding.
  - Agent 3: fluency, filler, repetition, and silence analysis.
  - Agent 4: visual/scene structure.
  - Agent 5: edit planning.
- RAG exists through Qdrant and supports course material uploads.
- The data model already stores videos, transcripts, segments, scenes, edit plans, and course materials.
- The frontend already has upload, processing, review, transcript, timeline, segment detail, stats, and export views.
- Renderer already trims, concatenates, burns subtitles, exports SRT/VTT/chapter/edit-plan JSON, and produces quality reports.
- Current code already has some useful academic evidence surfaces: edit plan JSON, chapters, quality report, action reasoning, and teacher overrides.

### Current Gaps

- The core model is still `Video`-centric, not `Project`-centric.
- It supports one uploaded video as the primary source, not separate screen, camera, audio, slides, and notes.
- AI providers are hardcoded mostly through `settings` and service singletons.
- There is no proper local/API/hybrid provider routing.
- Local transcription is not implemented.
- Settings are mostly environment based, not user-managed in the desktop app.
- Current UI is a review screen, not a guided professional editor workflow.
- Transcript editing is segment-based, not word/sentence-level editing.
- Timeline is a compact segment bar, not a multi-track editor timeline.
- Layout decisions are not first-class data. There is no layout engine for full slide, camera, side-by-side, or picture-in-picture.
- Polish tools such as annotations, selective captions, step labels, title cards, transitions, and callouts are not first-class entities.
- Export presets are file downloads, not explicit platform presets.
- The renderer is mainly trim/concat/subtitle oriented and not ready for multi-track composition.
- Current comments and README contain encoding artifacts that should be cleaned gradually during touched-file refactors.

## Target Architecture

### Core Concepts

The overhaul should introduce these first-class entities:

- `Project`: top-level editing workspace.
- `ProjectAsset`: uploaded or recorded source media/material.
- `MediaSource`: typed source such as screen video, camera video, mixed video, audio, slide deck, PDF notes, transcript, image, or B-roll.
- `Transcript`: word-level and segment-level speech record linked to a source or project.
- `EditDecision`: a timeline-aware action such as keep, cut, shorten, highlight, caption, annotate, layout change, or transition.
- `EditPlan`: structured plan generated by AI and modified by the user.
- `TimelineTrack`: screen, camera, audio, captions, overlays, annotations, titles, and B-roll.
- `LayoutCue`: timed layout instruction such as full screen, full camera, side-by-side, or picture-in-picture.
- `ExportPreset`: target output format and constraints.

### AI Provider Layer

The system should introduce an AI provider abstraction before adding more models.

Provider categories:

- Transcription provider.
- Chat/reasoning provider.
- Vision provider.
- Embedding provider.
- Local model runtime provider.

Processing modes:

- API mode: best accuracy, easiest to run, internet and cost required.
- Local mode: private/offline/free after model download, slower and hardware-dependent.
- Hybrid mode: local for cheap/private tasks, API for high-accuracy planning and visual reasoning.

Recommended default:

- Hybrid mode.
- Local transcription when available.
- API or strong model for content understanding and edit planning.
- Local deterministic passes for silence, basic filler detection, and simple validation.

### Provider Routing Matrix

| Pipeline Stage | API Option | Local Option | Recommended Default |
| --- | --- | --- | --- |
| Transcription | Mistral/Voxtral, OpenAI Whisper | whisper.cpp | Hybrid: local first, API fallback |
| Filler/dead-air detection | LLM + audio models | ffmpeg, VAD, local rules | Local deterministic plus optional LLM |
| Content understanding | DeepSeek, Gemini, OpenAI, Mistral | Ollama/llama.cpp model | API for accuracy, local optional |
| RAG embeddings | OpenAI or provider embeddings | local embedding model | API initially, local later |
| Visual understanding | vision API | local vision model, scene detection | PySceneDetect plus API vision later |
| Edit planning | strong JSON/reasoning LLM | local LLM | API initially, local fallback |
| Layout planning | LLM + rules | rules/local LLM | rules plus API reasoning |
| Rendering | FFmpeg/Remotion-like compositor | local rendering | local rendering |

## Data Model Migration Strategy

Do not immediately delete the current `Video` model. Instead, evolve in layers.

Recommended path:

1. Add `Project`.
2. Add `ProjectAsset`.
3. Link current `Video` to `ProjectAsset` as a legacy/mixed source.
4. Add `TimelineTrack` and `EditDecision`.
5. Keep current `Segment` and `EditPlan` while adding v2 fields.
6. Move renderer gradually from segment-only to edit-decision/timeline based.
7. Once stable, deprecate direct video-only assumptions.

This reduces risk because the old demo path can continue working during the overhaul.

The redesigned UI should be guided, dense, and professional.

Primary screens:

  - Transcribe
  - Clean
  - Sections
  - Layout
  - Polish
  - Export
- Settings:
  - AI mode and API keys.
  - Local models.
  - Export folder and presets.
  - Appearance.
  - Shortcuts and guided tours.

Editor layout:

- Left: transcript or source/navigation panel.
- Center: video preview and timeline.
- Right: current step controls.
- Bottom: multi-track timeline when the layout engine arrives.

## Testing Without Real Lecture Videos

Real videos are not required for early phases.

Early test assets can be generated or synthetic:

- short silent/voice audio files
- generated slides as images/video
- dummy screen recording video
- dummy camera video
- short combined MP4
- synthetic transcript JSON

Real assets become important in later phases:

- transcription accuracy
- Malay-English/Manglish handling
- topic segmentation quality
- screen/camera synchronization
- AI layout naturalness
- final demo evidence

## Academic Evaluation Plan

Evaluation should cover:

- Transcription quality by provider and mode.
- Processing time by provider and mode.
- Estimated cost per video for API/hybrid mode.
- Segment decision quality through human review.
- Silence/filler detection effectiveness.
- Topic segmentation quality.
- Output video duration reduction.
- Teacher override rate.
- Final perceived video quality from reviewers.

Recommended comparisons:

- API vs local vs hybrid.
- With slides/notes vs without slides/notes.
- Short video vs long lecture.
- Single combined video vs separate screen/camera/audio sources.
